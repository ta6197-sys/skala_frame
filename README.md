# 전체적인 구조

가능하면 원래 있던 폴더와 파일을 그대로 활용해서 코드를 만들려고 했다. 이미 갖고 있던 파일을 복사해서 쓸 수 있으면 최대한 그렇게 진행했다.
또한 리드미 파일을 쓸때도 칼럼명이나 어려운 단어, 영어 단어는 가능하면 사용 하지 않았음. 어차피 모르는 단어를 리드미 파일에 적어도 의미가 크게 없을 것으로 판단 내가 이해할 수 있도록 작성하려고 노력함.

## 1. 배열 렌더링

임의의 날씨 데이터 배열을 화면에 카드 형태로 반복해서 보여주는 게 목표였다. 반복되는 항목을 구분하는 값으로 순서 번호 대신 도시마다 갖고 있는 고유 번호를 쓰기로 했다. 순서 번호를 쓰면 배열 중간의 항목이 지워지거나 순서가 바뀔 때 화면이 엉뚱하게 재사용되는 문제가 생길 수 있기 때문이다.

## 2. 조건부 렌더링

v/of / v-else 사용: 기온이 25도 이상인 도시는 "더움", 25도 미만인 도시는 "선선함" 이라는 라벨을 붙이는 과제. 기준 온도는 그대로 25도로 두고 진행했다. 조건에 따라 둘 중 하나의 문구를 보여주는 문법으로 라벨을 나누고, 색상 구분은 배열 형태로 여러 클래스를 함께 지정하는 방식으로 처리했다. 공통 모양을 담당하는 기본 클래스가 하나 있고, 더움과 선선함 각각에 색만 덮어씌우는 클래스가 따로 있는 구조다.

## 3. 양방향 바인딩과 한글 처리

도시 이름을 한글로 검색하는 입력창을 만들고, 입력한 도시명을 그대로 화면에 출력하는 과제. 처음에는 값을 자동으로 양방향 연결해주는 문법으로 짰는데, 한글을 입력할 때 화면 반영이 한 박자 밀리는 문제가 있었다. 알아보니 한글처럼 여러 키 입력이 모여 한 글자로 완성되는 문자는, 조합이 끝나기 전까지의 입력 이벤트를 이 문법이 일부러 무시하기 때문. 그래서 value + @input을 사용하여 조합 중인 글자까지 실시간으로 반영됐다. 요구사항이 검색 필터링이 아니라 입력한 도시를 그대로 출력하는 것이었기 때문에 입력값을 가공 없이 그대로 보여줬다.

## 4. 이벤트와 이벤트 수식어

지역별 날씨 카드를 누르면 하단 상태바에 "그 도시가 선택되었습니다" 라는 문구가 뜨고, 카드 안의 상세보기 버튼을 누르면 팝업창으로 해당 도시의 날씨 내용이 뜨는데 이때 카드 선택까지 같이 일어나면 안 되는 과제였다. 카드와 버튼, 즉 부모 요소와 자식 요소가 일부러 겹쳐 있는 구조였다. 버블링을 막는 처리가 없으면 버튼을 눌렀을 때 팝업이 뜨고 이어서 부모 카드의 클릭까지 같이 실행돼서 상태바까지 바뀌어버렸다. 그래서 카드 전체에는 클릭 이벤트를 걸어 내부 어디를 눌러도 선택되게 하고, 상세보기 버튼에는 이벤트가 부모로 전파되지 않도록 막는 수식어를 따로 붙였다. 그 결과 버튼을 누르면 팝업만 뜨고 카드 선택 상태는 그대로 유지된다.

## 5. 나만의 추가

습도를 게이지 막대 형태로 표현하는 기능을 추가했다. 여기에 체감온도, 풍속, 강수확률까지 더 넣어서 정보량을 늘렸다. 미세먼지 농도는 좋음, 보통, 나쁨 세 단계로 나눠서 화면에 표시했다. 즐겨찾기 기능도 넣었는데, 여러 개를 동시에 체크할 수 있는 형태로 만들고 이 체크박스에도 이벤트 전파를 막는 처리를 걸어서 즐겨찾기 등록이 카드 선택과 섞이지 않게 했다. 마지막으로 상세 정보 패널을 열고 닫는 기능을 넣었는데, 지금 열려 있는 카드의 번호 하나만 저장해서 한 번에 한 카드만 열리게 했고, 같은 버튼을 다시 누르면 닫히게 만들었다. 기존의 상세보기 팝업 버튼은 그대로 남겨뒀다.

# 과제 2

1일차 때 쓰던 날씨 데이터와 스타일 파일을 그대로 재사용했다. 1일차와 마찬가지로 모든 요구사항이 합쳐진 완성본 하나와, 요구사항별로 따로 만든 개별 파일 다섯 개, 이렇게 두 가지 형태로 구성했다. 개별 파일끼리는 서로 상태를 공유하지 않고 각자 필요한 값을 자기 파일 안에서 다시 선언하게 했다. 파일 하나만 열어봐도 그 요구사항이 뭘 하는지 바로 파악할 수 있게 하려는 의도였다.

## 1. 반응형 상태 관리

검색어, 선택된 도시 정보, 지역별 날씨 데이터 배열을 반응형 상태로 정의하는 과제였다\\. 1일차 때 쓰던 변수 이름을 그대로 안 쓰고 새로운 이름으로 바꿨다. 원래는 선택된 도시를 이름 문자열 하나로만 담았는데, 값이 바뀌는 걸 감시하는 콜백 안에서 도시의 여러 속성에 접근해야 해서 도시 객체 전체를 저장하는 방식으로 바꿨다.

## 2. 검색 도시 (계산된 값 활용)

전체 날씨 목록 중에서 사용자가 입력한 검색어가 도시 이름에 포함된 항목만 걸러서, 원본이 바뀌면 자동으로 다시 계산되는 값 하나에 담아두는 과제. 검색어가 도시 이름에 포함되는지 확인하는 배열 필터링 함수로 구현했다. 검색어가 빈 문자열일 때는 "포함되어 있는지" 확인하는 함수가 항상 참을 반환하기 때문에, 별도의 예외 처리 없이도 걸러진 목록이 자동으로 원본 전체와 같아진다. 이 성질을 검색 결과를 보여주는 요구사항에서 그대로 활용했다.

## 3. 값 변화 감시

watch/watchEffect: 선택된 도시 정보가 바뀔 때마다 콘솔에 로그를 남기고, 검색어를 타이핑할 때마다 변하는 값을 추적해서 역시 콘솔에 로그를 남기는 과제. 값 변화를 감시하는 방법이 두 가지가 있는데, 하나는 감시할 대상을 명시적으로 지정하고 콜백에서 이전 값과 새 값을 둘 다 받을 수 있는 방식이고, 이번 과제에서 도시 정보처럼 "값이 바뀌기 전과 후"를 비교해야 하는 곳에 이 방식을 썼다. 다른 하나는 감시 대상을 따로 적지 않아도 콜백 안에서 참조하는 반응형 값을 알아서 추적해주는 방식인데, 대신 이전 값은 받을 수 없어서 검색어처럼 타이핑마다 자동으로 다시 실행되기만 하면 되는 곳에 썼다. 두 방식의 콘솔 로그 문구를 다르게 남겨서 어떤 방식으로 실행됐는지 로그만 보고도 구분할 수 있게 했다.

## 4. 검색 결과 표시

검색어가 비어 있을 때는 원본 데이터를, 검색어와 일치하는 데이터가 있을 때는 그 데이터를, 일치하는 도시가 없을 때는 안내 문구를 보여주는 과제였다. 조건을 세 갈래로 나눠서 마크업을 여러 번 쓰는 대신, 걸러진 목록 하나만으로 반복 출력을 돌리고 그 결과가 0개일 때만 안내 문구를 추가로 띄우는 방식으로 단순화했다. 앞서 설명한 계산된 값의 성질 덕분에 가능한 방법이었다.

## 5. 나만의 추가

즐겨찾기 개수를 계산된 값으로 뽑아내고, 그 값이 바뀔 때마다 감시 기능으로 콘솔에 몇 개에서 몇 개로 바뀌었는지 로그를 남기도록 추가했다.

# 과제 3

1~2일차 때 쓰던 데이터와 스타일 파일을 그대로 재사용했다. 과제 2의 통합 완성본을 기준으로 기능은 하나도 바꾸지 않고 파일만 여러 개로 쪼개는 것이 목표. 분리 전과 후를 나란히 비교할 수 있게 하려는 의도였다. 모든 상태와 감시 로직은 최상위 부모 컴포넌트 한 곳에만 두고, 나머지 자식 컴포넌트는 전달받은 값으로 화면만 그리는 구조로 통일했다.
단방향 데이터 구조, container/presentational패턴 사용

## 1. 최상위 부모 컴포넌트

기존에 있던 모든 반응형 데이터를 이 파일로 옮겼다. 변수 이름도 그대로 유지했다. 자식이 알려준 값을 받아서 상태를 고치는 처리 함수만 새로 추가했다. 데이터를 부모 한 곳에 몰아두면 어떤 카드가 열려 있는지, 어떤 도시가 즐겨찾기인지를 한 곳에서 판단할 수 있어서 카드끼리 상태가 어긋날 일이 없다.

## 2. 공통 카드 컴포넌트

검색박스와 목록박스의 디자인을 공통화해서, 부모 컴포넌트가 내용을 끼워 넣을 수 있는 자리를 마련해두는 과제. 스크립트 영역은 아예 비워두고 테두리와 배경, 제목 위치 같은 껍데기 역할만 담당하게 했다. 제목을 넣는 자리와 본문을 넣는 자리를 이름으로 구분해서 따로 마련했는데, 검색박스와 목록박스가 "제목 + 내용" 구조로 똑같이 생겨서 이 방식이 잘 맞아떨어졌다. 두 자리 모두 기본값을 넣어둬서 부모가 아무것도 채우지 않아도 화면이 비어 보이지 않도록 진행. 이 공통 컴포넌트는 검색박스, 즐겨찾기, 목록박스 세 군데에서 재사용된다.

## 3. 검색창 컴포넌트

부모로부터 검색어 값을 전달받아 표시하고, 도시를 검색하면 검색어가 바뀌었다는 신호를 부모에게 전달하는 과제. 자식이 부모의 값을 직접 고칠 수 없는 구조라서, 과제 1에서 썼던 값 표시와 입력 이벤트를 직접 연결하는 방식이 오히려 그대로 맞아떨어졌다. 값을 받아서 화면에 표시하고, 입력이 일어나면 새 값을 신호로 만들어 부모에게 되돌려 보내는 식이다. 결국 편한 양방향 문법이 내부적으로 하던 일을 부모와 자식 사이에서 다시 한 번 손으로 풀어 쓴 셈이고, 한글 조합 중인 글자까지 실시간으로 반영되는 성질도 과제 1과 똑같이 유지된다.

## 4. 날씨 카드 컴포넌트

선택된 도시 객체를 전달받아 표시하고, 카드를 선택하는 신호와 상세보기 신호를 각각 부모에게 전달하는 과제. 도시 객체 하나만 전달받아서 카드 한 장만 그리도록 만들고, 반복 출력과 고유 번호 지정은 부모 쪽에 그대로 남겨뒀다. 카드 전체를 누르면 선택 신호를, 상세보기 버튼을 누르면 이벤트 전파를 막은 채로 상세보기 신호를 보낸다.
실제 팝업창은 부모가 띄우기 때문에 자식은 "눌렸다"는 사실만 알리는 역할이다. 이벤트 전파를 막는 처리를 자식 안에 그대로 둔 이유는, 버블링은 부모와 자식 컴포넌트 사이의 문제가 아니라 화면 요소 자체의 문제라서 카드 안에서 막아야 신호 자체가 두 번 일어나지 않기 때문이다. 즐겨찾기 체크박스는 아직 배운 문법으로는 자식이 값을 직접 고칠 수 없어서, 상태를 받아서 표시만 하고 변경이 일어나면 신호를 보내는 형태로 만들었다. 배열에 넣고 빼는 실제 판단은 부모가 한다. 상세 패널도 같은 이유로 열림 여부만 참거짓 값으로 전달받고, 버튼을 누르면 신호만 보낸다.

## 5. 스타일 분리

컴포넌트별로 파일을 분리하면서, 각 컴포넌트에 해당하는 디자인은 그 파일 안에서만 적용되는 스타일 블록으로 각각 옮겼다. 한 파일에 몰려 있던 스타일을 잘라서 카드, 뱃지, 게이지, 상태바 컴포넌트가 각자 자기 것만 갖게 했다. 기존 공통 스타일 파일은 과제 1, 2가 계속 쓰고 있어서 지우지 않고 그대로 뒀다. 클래스 이름이 겹치지만 컴포넌트 전용 스타일은 자동으로 붙는 속성 선택자 때문에 우선순위가 더 높고 값도 동일해서 화면은 그대로 유지됐다. 다만 즐겨찾기 바가 공통 카드 컴포넌트 안으로 들어가면서 테두리가 이중으로 보이는 문제가 있어서, 기존 전역 스타일을 물려받지 않도록 클래스 이름을 바꿨다.

## 6. 슬롯과 스코프 확인

내용을 끼워 넣는 자리로 전달되는 자식 컴포넌트는 화면상으로는 공통 카드 컴포넌트 안에 있지만, 실제로는 부모 컴포넌트의 영역에서 해석된다는 걸 확인하는 과제였다. 그래서 검색창과 날씨 카드를 공통 카드 컴포넌트 안에 넣었는데도, 값 전달과 신호 연결을 최상위 부모가 직접 걸 수 있었다.
만약 이런 성질이 없었다면 공통 카드 컴포넌트가 값을 한 번 받아서 다시 자식에게 넘기는 중계 코드라는 것을 사용해야함. 즐겨찾기 바는 공통 카드 컴포넌트가 아니라 최상위 부모의 전용 스타일이 그대로 적용됐다.

## 7. 나만의 추가

하단 상태바를 별도 컴포넌트로 분리했다. 선택된 도시 객체만 전달받아 문구를 출력하는, 전달받은 값만 쓰는 가장 단순한 형태다. 기온 뱃지와 미세먼지 뱃지가 생김새가 완전히 같아서 하나의 뱃지 컴포넌트로 합쳤고, 종류와 문구만 전달받아 색을 다르게 표시하도록 만들어서 카드 한 장에서 두 번 재사용되게 했다. 습도 게이지 바도 따로 떼어내서, 습도 숫자 하나만 전달받아 막대 너비를 계산하게 하니 카드 쪽 코드가 훨씬 짧아졌다. 이 세 컴포넌트는 전부 신호를 보내지 않는 표시 전용이라서, 신호를 보내야 하는 검색창이나 날씨 카드와는 역할이 확실히 나뉜다.

# 과제 4

1~3일차 때 쓰던 데이터와 스타일 파일을 그대로 재사용했다. 과제 3의 최상위 부모 컴포넌트를 기준으로, 기능은 그대로 두고 한 화면에 다 있던 것을 주소별 페이지로 쪼개는 것이 목표였다. 이전 과제 파일은 그대로 두고 라우터와 페이지용 폴더를 새로 만들었다. 화면 껍데기가 라우터 구조로 바뀌면서 과제 1~3 화면이 사라지기 때문에, 기존 내용을 별도의 레거시 페이지로 옮겨서 다른 주소에서 계속 볼 수 있게 했다.

## 1. 라우터 설정과 지연 로딩

첫 화면(홈)만 앱을 켜자마자 바로 필요해서 처음부터 불러오게 했고, 나머지 페이지는 사용자가 그 주소로 들어갈 때 그제서야 내려받는 방식으로 진행. 첫 화면까지 나눠서 불러오면 요청만 한 번 더 생기기 때문이다. 실제로 빌드를 해보니 상세, 통계, 소개, 없는 페이지, 레거시 각 화면이 별도 파일로 떨어졌는데, 지연 로딩이 실제로 걸렸는지는 이렇게 빌드 결과로 확인하는 게 가장 확실했다. 알 수 없는 주소로 들어왔을 때 잡아주는 규칙은 라우터 목록의 맨 마지막에 뒀다. 라우터는 등록된 순서대로 훑기 때문에 이 규칙을 위로 올리면 다른 모든 주소가 먼저 여기에 걸려서 항상 404만 나옴. 주소 표시 방식은 해시 기호가 붙지 않는 깔끔한 형태로 골랐는데, 대신 어떤 주소로 새로고침해도 서버가 첫 화면 파일을 돌려줘야 하고, 개발용 서버는 기본적으로 그렇게 동작하기 때문에 문제없이 잘 됐다.

## 2. 전체 화면 껍데기

기존에 화면 껍데기 역할을 하던 파일에서 컴포넌트를 불러오는 코드를 전부 걷어내고 스크립트 영역을 비웠다. 메뉴는 일반 링크 태그가 아니라 라우터 전용 링크로 만들었다. 일반 링크를 쓰면 브라우저가 페이지를 통째로 다시 받아와서 새로고침 없이 화면이 바뀌는 방식이 아니게 되는데, 라우터 전용 링크는 클릭을 가로채서 주소만 바꿔준다. 현재 위치한 메뉴 표시는 직접 만들지 않고 라우터가 자동으로 붙여주는 활성 클래스에 색만 입혔다. 다만 홈 링크는 모든 주소의 앞부분과 겹치기 때문에, 정확히 일치할 때만 활성화되는 방식을 대신 썼다. 그렇지 않으면 다른 페이지에 있을 때도 홈 메뉴가 같이 켜져 있는 문제가 생긴다.

## 3. 홈 페이지

기존 최상위 부모 컴포넌트가 갖고 있던 데이터와 감시 로직을 그대로 옮겼다. 변수 이름도 처리 함수 이름도 안 바꿨다. 달라진 건 "부모 컴포넌트"였던 것이 "홈 주소의 페이지"가 됐다는 점뿐이고, 상태는 전부 여기 두고 자식은 전달받은 값으로 그리기만 하는 구조는 과제 3과 동일. 상세보기 버튼을 누르면 팝업창을 띄우는 대신 그 도시의 상세 주소로 이동하도록 바꿨다. 팝업은 잠깐 떴다 사라지지만 페이지 이동은 진짜 다른 화면이 열리는 거라, 그 주소를 복사해서 다시 들어갈 수 있다는 차이가 있다. 이동에 필요한 건 도시 이름이 아니라 고유 번호라서, 자식이 보내는 신호 값도 도시 객체 전체에서 고유 번호로 바꿨다. 열림 여부만 저장해서 관리하던 상세 패널은 없앴다. 상세 정보를 보여주는 역할이 별도 페이지로 넘어갔는데 카드 안에도 같은 게 남아 있으면 역할이 겹치기 때문이다.

나만의 추가로 검색어를 화면 안에만 두지 않고 주소창의 물음표 뒤 검색 조건에도 함께 기록되게 했다. 검색한 상태로 새로고침하거나 주소를 복사해서 열어도 결과가 그대로 유지된다. 페이지에 들어올 때는 주소에 담긴 검색어를 읽어서 화면 상태에 넣고, 검색어가 바뀌면 반대로 주소를 갱신하는 양방향 구조로 만들었다. 주소를 바꿀 때는 이동 기록을 새로 쌓는 방식 대신 현재 기록을 덮어쓰는 방식을 썼다. 새로 쌓는 방식을 쓰면 글자를 한 자 칠 때마다 이동 기록이 쌓여서 뒤로 가기를 여러 번 눌러야 홈을 빠져나가게 된다. 검색어를 다 지우면 주소도 깔끔하게 원래 주소로 돌아가도록 처리.

## 4. 상세 페이지

지역별 상세 기상관측 정보를 보여주는 페이지다. 라우터 경로에 도시 고유 번호를 파라미터로 넣는 방식으로 잡아서, 주소의 도시 코드 부분을 그대로 읽어올 수 있게 진행. 화면이 마운트되는 시점에 이 값을 기준으로 임시 데이터에서 해당 도시 객체를 찾아 화면에 담았다. 여기서 한 번 막혔던 부분이 있는데, 같은 상세 페이지 안에서 다른 도시로 이동하면 화면이 안 바뀌는 문제였다. 같은 라우트끼리의 이동이라 화면 컴포넌트를 새로 만들지 않고 재사용하기 때문에, 마운트 시점에만 실행되는 코드는 다시 실행되지 않는 것이었다. 그래서 주소의 파라미터 값이 바뀌는 것도 함께 감시하도록 추가했다. 최초 진입은 마운트 시점 처리가, 같은 페이지 안에서의 이동은 값 감시가 담당하는 셈이다. 이미 카드에서 보여주고 있는 데이터를 표로 펼치고, 체감온도와 실제 기온의 차이를 문장으로 계산해서 붙였다. 형식은 맞는데 실제로 없는 도시 코드로 들어온 경우에는 없는 페이지로 처리하지 않고 안내 문구와 돌아가기 버튼을 띄웠다. 주소 자체는 라우터가 아는 형식이 맞으니 없는 페이지가 아니라 없는 데이터이기 때문.

## 5. 소개 페이지

상태가 하나도 없는 정적인 페이지라서 지연 로딩 대상으로 두기 딱 좋았다. 어떤 앱인지, 어떤 주소가 있는지, 어떤 라우터 기능을 썼는지 세 덩어리로 나눠서 적었다. 껍데기는 과제 3에서 만든 공통 카드 컴포넌트를 그대로 재사용했다. 돌아가기는 링크가 아니라 버튼과 코드로 직접 이동하는 방식으로 만들었다. 요구사항이 버튼이기도 했고, 링크로 이동하는 것과 코드로 이동하는 것을 한 화면 안에서 둘 다 보여주고 싶었다.

## 6. 나만의 추가

정의된 페이지 외에 통계 페이지를 하나 더 만들어서 라우팅했다. 도시 여섯 곳을 전부 집계해서 평균 기온과 평균 습도, 가장 덥고 가장 추운 도시, 기온 순위 막대, 미세먼지가 나쁨인 도시와 강수확률이 높은 도시 목록을 계산된 값만으로 보여준다. 페이지끼리 상태를 공유하는 방법은 아직 배우지 않아서, 임시 데이터만 있으면 혼자 다 계산되는 주제로 골랐다. 즐겨찾기 모아보기 같은 걸 만들려면 홈의 상태를 넘겨야 해서 이번 과제 범위를 벗어난다.
순위는 원본 배열을 직접 정렬하지 않고 복사본을 만들어서 정렬했다. 원본을 그대로 정렬하면 다른 화면의 도시 순서까지 같이 바뀌기 때문이다. 막대 길이는 가장 더운 도시를 기준으로 비율을 계산했고, 습도 게이지와 같은 방식이다. 순위 행을 누르면 그 도시의 상세 페이지로 이동하게 만들어서, 홈이 아닌 다른 화면에서도 상세 페이지로 들어갈 수 있도록 진행. 없는 페이지로 갈 때 잡아주는 화면은 어떤 주소로 잘못 들어왔는지 함께 보여줘서 오타인지 정말 없는 페이지인지 바로 구분되게 했다.

## 7. 확인한 것

홈에서 상세보기를 누르면 주소가 상세 페이지로 바뀌고, 그 주소에서 새로고침해도 데이터가 그대로 뜬다. 상세 페이지에서 이전, 다음 도시를 눌러도 화면이 잘 바뀐다. 없는 도시 코드로 들어가면 안내 문구가, 아예 없는 주소로 들어가면 404 페이지가 뜸. 검색 조건을 담은 주소로 바로 들어가면 검색창에 값이 채워지고 결과도 그에 맞게 걸러진다. 빌드 결과에서 페이지별 파일이 따로 생성되는 것으로 지연 로딩이 걸린 걸 확인했다.

# 과제 5

 과제 4까지는 상태가 화면마다 흩어져 있었는데, 그중 화면이 바뀌어도 남아 있어야 하는 값만 골라서 전역 저장소로 올리는 것이 목표였다. 저장소는 세 개를 만들었다. 단위와 개인 기준 설정을 담는 저장소, 즐겨찾기 저장소, 최근 본 도시 저장소다. 반대로 검색어나 선택된 카드처럼 그 화면을 벗어나면 의미가 없는 값은 일부러 전역으로 올리지 않고 그 화면만의 지역 상태로 남겨뒀다. 전역에 둘 값과 화면에 둘 값을 나누는 게 핵심

## 1. 단위 설정 저장소

섭씨, 화씨 단위를 저장하는 상태와, 현재 단위에 맞는 기호를 돌려주는 계산 값, 두 단위를 서로 바꿔주는 실행 함수로 구성했다. 함수형으로 저장소를 작성해서, 지금까지 써오던 컴포지션 문법을 그대로 쓸 수 있었다. 저장소를 구분하는 이름은 파일마다 겹치지 않게 붙였다. 밖으로 내보내는 값만 외부에서 보이는 구조라서, 내부에서만 쓰는 상수는 자연스럽게 감춰졌다.

## 2. 단위 전환 버튼 컴포넌트

전달받는 값도 보내는 신호도 없는 컴포넌트가 됐다. 부모에게 값을 받지도 알리지도 않고 저장소를 직접 읽고 직접 고친다. 과제 3에서 검색창을 만들 때는 검색어를 전달받고 신호로 되돌려주는 중계를 직접 짰는데, 그 중계가 통째로 없어진 셈이다. 전역 저장소를 왜 쓰는지가 이 파일 하나에서 가장 잘 드러났다. 표시 문구도 화면마다 다시 만들지 않고 저장소 쪽의 계산 값 하나로 빼둬서, 나중에 설정 화면에서도 같은 문구를 재사용할 수 있었음.

상단 메뉴 옆에 이 버튼을 배치했다. 요소가 늘어나면서 좁은 화면에서 메뉴가 잘리는 문제가 있어서 줄바꿈이 되도록 조정했다. 겸사겸사 즐겨찾기 메뉴에 개수 배지를 붙였는데, 화면 껍데기 파일이 어느 페이지의 부모도 아니라서 전달받는 값 방식으로는 처리할 방법이 없었기 때문에 저장소를 직접 읽게 했다.

## 4. 단위 변환 적용

메인과 상세 화면에 단위 설정 변경을 적용하는 과제였는데, 같은 코드가 여러 화면에 반복되는 문제가 있었다. 반복 문제는 값을 계산해서 돌려주는 함수를 저장소의 계산 값 안에 두는 방식으로 풀었다. 인자를 받아서 그때그때 변환 결과를 돌려주는 함수 형태로 만드니, 변환 공식이 저장소 한 곳에만 남게 됐다. 실제로 카드, 상세, 통계 세 화면이 전부 이 함수 하나만 호출한다. 화씨 변환 공식은 프로젝트 전체에서 딱 한 줄만 존재한다. 체감온도도 같은 단위라서 함께 변환해야 했다. 기온만 바꾸면 화씨 모드에서 체감온도가 어긋나 보이기 때문이다. 체감온도와 실제 기온의 차이를 설명하는 문구도 변환된 값끼리 계산하도록 고쳤다. 섭씨로는 작은 차이도 화씨로 환산하면 값이 달라져서 원본끼리 계산하면 화면에 보이는 숫자와 안 맞기 때문이다. 통계 화면의 평균 기온은 섭씨 원본으로 먼저 평균을 낸 다음 마지막에 한 번만 변환했다.  반대로 기온 순위 막대 길이는 일부러 섭씨 원본으로 계산했다. 화씨는 0이 기준점이 아니기 때문에 변환된 값으로 비율을 계산하면 막대 길이가 전부 비슷하게 뭉개지기 때문. 더움과 선선함 판정도 항상 섭씨 원본을 기준으로 했다. 단위를 바꿨다고 실제 더위가 바뀌는 건 아니기 때문이다.

## 5. 나만의 추가 (1) - 즐겨찾기 저장소

과제 4까지 즐겨찾기는 홈 페이지의 지역 상태였다. 그래서 카드를 체크하고 상세보기로 들어갔다 돌아오면 체크가 전부 풀려 있었다. 홈 화면이 사라지면서 그 값도 같이 사라졌기 때문이다. 전역 저장소로 올리니 화면을 옮겨도 값이 남았고, 과제 4에서 만들지 못했던 즐겨찾기 모아보기 화면도 새로 만들 수 있었다. 도시 이름이 아니라 고유 번호를 담도록 했다. 이름은 표시용이고 고유 번호가 데이터를 찾는 열쇠라서, 목록을 다시 그릴 때 훨씬 편했다. 즐겨찾기 여부를 확인하는 값도 인자를 받는 계산 함수로 만들었다. 카드마다 자기가 즐겨찾기인지 물어봐야 하는데, 도시별로 각각의 계산 값을 따로 만들 수는 없기 때문이다. 날씨 카드 컴포넌트에서는 즐겨찾기 관련 전달값과 신호가 사라지고, 대신 카드 선택과 상세보기 신호는 그대로 남겼다. 즐겨찾기는 데이터라서 저장소가 갖고, 어느 주소로 이동할지는 그 화면의 결정이라 여전히 부모가 처리하는 게 맞다고 판단했다. 즐겨찾기 모아보기 페이지는 자기 상태가 하나도 없다. 저장소에서 즐겨찾기 도시 목록을 읽어서 카드를 반복 출력하는 게 전부라 파일이 아주 짧아졌다.

## 6. 나만의 추가 (2) - 최근 본 도시 저장소

상세 페이지에 들어갈 때마다 도시 번호를 기록해두고, 홈 화면 상단에서 칩 형태로 꺼내 쓴다. 기록하는 화면과 보여주는 화면이 아예 다른 페이지라서 전달값으로는 애초에 전달할 방법이 없다. 즐겨찾기보다 이쪽이 전역 저장소가 아니면 안 되는 경우에 더 가깝다. 새로 기록하는 함수는 이미 본 도시면 기존 자리에서 빼고 맨 앞에 다시 넣는 방식으로 만들어서, 중복 없이 최신순이 유지되고 최대 다섯 개까지만 남는다. 기록은 도시를 실제로 찾은 경우에만 하도록 했다. 없는 도시 코드로 들어온 것까지 이력에 남으면 안 되기 때문이다.

## 7. 나만의 추가 (3) - 개인 기준 설정

과제 1에서 "25도 이상이면 더움" 같은 기준이나 미세먼지 등급 기준은 원래 임의로 정한 숫자였다. 이 숫자들을 사용자가 직접 바꿀 수 있도록 단위 설정 저장소의 상태로 옮겼다. 판정 자체도 저장소의 계산 값으로 올려서, 원래 카드, 상세, 통계 세 곳에 흩어져 있던 숫자가 전부 저장소 한 곳을 보게 만들었다. 앞서 온도 변환식을 모은 것과 같은 방식이다. 미세먼지 등급 계산은 문구가 아니라 등급 이름만 돌려주게 해서, 뱃지 색이나 문구는 화면마다 다를 수 있게 판정과 표현을 나눴다. 설정 화면의 슬라이더는 값을 직접 저장소에 대입하지 않고, 값을 검증하는 실행 함수를 거치도록 만들었다. 좋음 상한이 나쁨 하한을 넘어가면 등급 판정이 뒤집히기 때문에, 실행 함수 안에서 최소값과 최대값을 비교해서 막았다. 실제로 좋음 기준을 나쁨 기준보다 크게 넣어보면 나쁨 기준이 밀려나는 걸 확인했다. 설정 화면에는 미리보기를 넣어서 기준을 옮기면 지금 데이터가 어떻게 갈리는지 바로 보이게 진행.

## 8. 나만의 추가 (4) - 생활지수와 옷차림 추천

원본 관측값을 조합해서 새로운 정보를 만들어내는 것도 해보고 싶어서 상세 페이지에 두 가지를 추가했다. 생활지수는 빨래, 세차, 외출 세 가지를 점수로 환산한다. 계산은 순수 함수로 따로 두고 화면은 결과만 받아서 반복 출력한다. 이건 일부러 전역 저장소로 만들지 않았다. 도시 하나만 넣으면 답이 정해지는 계산이고 여러 화면이 공유하는 값도 아니라서, 저장소에 넣으면 오히려 왜 넣었는지 설명이 안 된다. 전역 저장소는 화면 사이에 공유되는 상태를 담는 자리라는 기준을 그대로 적용했다. 앞서 기온 뱃지와 미세먼지 뱃지를 하나로 합쳤던 것과 같은 판단이다. 옷차림 추천은 체감온도를 다섯 단계로 나눠서 판정하는데, 여기에 개인 체질 보정을 얹었다. 옷차림 추천 컴포넌트는 표시 전용이 아니라 저장소를 직접 읽는 컴포넌트가 됐다. 옷차림은 도시 데이터만으로는 정해지지 않고 사람의 설정이 있어야 정해지기 때문이다. 판정에 쓰는 온도는 항상 섭씨 원본 기준으로 했다. 단위를 화씨로 바꿨다고 입을 옷이 달라지지는 않기 때문이다. 강수확률이 높으면 우산을, 미세먼지가 나쁨 등급이면 마스크를, 풍속이 강하면 바람막이를 따로 덧붙였다. 이 중 마스크 판정도 앞서 만든 미세먼지 등급 계산을 그대로 썼다.

## 9. 확인한 것

단위를 바꾸면 홈 카드, 상세 페이지, 통계 화면이 동시에 화씨로 바뀐다. 카드를 체크하고 상세보기로 들어갔다 돌아와도 체크가 유지. 과제 4에서는 풀렸던 부분이다. 상세 페이지에서 즐겨찾기를 추가하면 메뉴의 개수 배지와 모아보기 목록이 같이 갱신된다. 설정에서 더움 기준을 올리면 카드 뱃지 문구가 전부 바뀌고 통계의 순위 막대 색까지 같이 바뀐다. 미세먼지 좋음 기준을 나쁨 기준보다 크게 넣어도 값이 뒤집히지 않는다. 체질을 바꾸면 옷차림 판정 문구와 근거가 같이 바뀐다. 빌드는 문제없이 성공했다. 다만 브라우저를 새로고침하면 저장소 값이 전부 초기화되는데, 전역 저장소는 원래 메모리에만 사는 게 정상이고, 값을 브라우저에 남기는 방법은 범위 밖이라고 판단

# 이후~

과제 5까지는 데이터가 전부 임시 데이터라 네트워크 요청이 한 건도 없었다. 이번 과제는 새 기능을 얹는 것보다 이미 만들어둔 기능의 바닥을 실제 관측값으로 갈아끼우는 게 핵심이라고 생각했다. 그래서 화면과 계산식은 거의 손대지 않고, 데이터가 오는 길을 새로 만드는 데 시간을 다 썼다. 도시 수를 늘리는 것보다 도시 하나에 대해 더 많이 아는 쪽이 이번 요구사항, 즉 외부 서비스를 추가해서 기능을 확장하는 것에 더 맞는다고 판단했다. 별도의 백엔드 서버는 띄우지 않았고, 브라우저가 외부 서비스를 직접 호출하는 구조.

## 1. 외부 날씨 서비스 연동 준비

외부 서비스를 호출하는 라이브러리를 설치하고 계정을 만들어 인증 키를 발급. 키는 환경변수 파일에 넣고 이 파일을 저장소에는 올리지 않도록 처리했다. 소스코드에 키를 그대로 박아두지 않은 이유가 두 가지다. 하나는 본인이 직접 발급받으라는 요구사항이었고, 다른 하나는 저장소에 한 번 올라간 키는 나중에 지워도 기록에는 계속 남기 때문이다. 다만 이 방법도 한계가 있다는 걸 알고 썼다. 이런 환경변수는 빌드 결과물에 문자열로 그대로 박혀서 개발자 도구로 다 보인다. 파일을 분리하는 건 브라우저에서 숨기는 게 아니라 저장소에만 남기지 않는다는 정도의 의미였다. 브라우저에서만 동작하는 앱에서는 키를 완전히 가릴 방법이 없고, 진짜 해결책은 키를 대신 들고 호출해주는 서버뿐이다. 이 한계는 나중에 배포 단계에서 실제로 해결했는데, 그 내용은 뒤쪽에 따로 적어뒀다.

## 2. 네 개의 층으로 나눈 구조

외부 서비스 호출을 화면에서 직접 하지 않기로 했다. 화면이 주소와 키를 알아버리면 나중에 서버가 생겼을 때 고쳐야 할 곳이 화면 개수만큼 늘어난다. 그래서 기본 주소와 공통 옵션, 인증 키, 실패 처리를 담당하는 파일 하나를 만들어서 주소와 키를 아는 유일한 곳으로 삼았다. 그 위에 "어떤 주소로 뭘 물어볼지"만 아는 함수들을 모은 파일을 뒀는데, 응답을 그대로 넘기지 않고 우리 앱에서 쓰는 이름으로 미리 번역해서 넘긴다. 여기서 번역을 끝내두니까 이전 과제까지 만든 화면과 계산식을 거의 안 건드려도 됐다. 그 위에는 도시별 관측값을 보관하고 로딩, 에러, 갱신 시각을 관리하는 전역 저장소를 뒀다. 요청이 성공하면 응답에서 실제 데이터만 벗겨서 넘기고, 실패하면 에러 메시지를 한국어 문장으로 바꿔서 넘기는 공통 처리도 넣어서, 화면에서는 그 문장만 그리면 끝나게 만들었다.

## 3. 도시 정보와 날씨 정보 분리

과제 5까지는 파일 하나가 도시가 뭔지와 지금 날씨가 어떤지를 같이 들고 있었다. 실제 외부 서비스를 붙이면서 이 둘을 갈랐다. 안 변하는 정보는 그대로 두고 변하는 정보만 통신하자는 생각이었다. 도시 이름 대신 위도, 경도 좌표를 기준으로 삼았다. 현재 날씨, 대기오염, 예보, 자외선 네 서비스가 전부 좌표를 공통으로 받고, 이름을 받는 건 현재 날씨 하나뿐이었기 때문이다. 덕분에 이름이 같은 도시가 겹칠 걱정도 없어졌다. 기존 임시 데이터 파일은 지우지 않고 남겨뒀는데, 통신이 실패했을 때 대신 보여줄 데이터로 쓰기 위함. 즐겨찾기 저장소와 최근 본 도시 저장소가 이 임시 데이터를 직접 참조하고 있었는데, 이 참조를 나눔. 즐겨찾기 저장소는 날씨 데이터가 필요하니 새로 만든 날씨 저장소를 보게 했고, 최근 본 도시 저장소는 이름만 있으면 되니 도시 정보 파일을 보게 했다.

## 4. 실제 날씨 데이터 적용

임시로 채워뒀던 값을 하나씩 실제 출처로 갈아끼웠다. 온도, 체감온도, 습도는 서비스 응답의 해당 항목에서, 풍속과 상태 문구도 각각 응답의 해당 항목에서 가져온다. 한국어로 표시되는 건 상태 문구뿐이고, 도시 이름은 여전히 영문으로 오길래 화면엔 미리 갖고 있던 한글 이름을 썼다. 응답 항목이 비어 있는 경우가 종종 있어서 값이 없을 때를 대비한 기본값 처리를 전부 붙였다. 값이 비어 있는 채로 화면까지 가면 조용히 이상한 숫자가 뜨는 걸 겪어봐서다. 실제 값은 소수점이 지저분하게 들어오길래 한 자리로 잘라서 썼다. 새로 만든 저장소는 날씨 저장소 하나뿐이다. 저장소로 올릴지 말지는 두 화면 이상이 같은 데이터를 쓰는지, 화면을 떠났다 돌아와도 값이 살아있어야 하는지 둘 중 하나라도 맞으면 올리는 식으로 판단. 도시 목록은 홈, 통계, 즐겨찾기가 다 같이 쓰니까 여기 해당됐다. 반대로 자외선, 내 위치 좌표, 검색어는 한 화면에서만 쓰니까 컴포넌트 안에 그냥 뒀다.

## 5. 외부 서비스 항목 추가

대기오염 정보를 추가해서, 지금까지 근거 없이 대충 넣었던 미세먼지 숫자를 실제 관측값으로 바꿨다. 여기서 생각지도 못한 소득, 설정 화면의 미세먼지 경계 기본값이 한국 환경부 등급 기준이랑 그대로 맞아떨어졌다. 과제 5까지는 그냥 임의로 정한 숫자였는데, 실제 관측값을 받아오는 순간 갑자기 근거 있는 숫자가 된 셈. 예보 정보도 추가해서 3시간 간격으로 여러 시점의 데이터를 받아왔다. 강수확률의 실제 출처이자 뒤에 나오는 나만의 추가 기능의 재료로 썼다. 강수확률은 0에서 1 사이 소수로 오기 때문에 100을 곱해줘야 퍼센트가 된다. 그냥 쓰면 강수확률 80퍼센트가 화면에 0.8퍼센트로 찍히는 웃긴 상황이 생긴다. 좌표를 한글 지명으로 바꿔주는 역지오코딩 기능도 추가했다. 한글 지명이 없는 지역은 영문 이름으로 떨어지게 해뒀다. 계획과 달라진 부분도 있다. 두 화면 이상이 쓰는 데이터라서 전역 저장소로 올렸고, 결과적으로 상세 페이지에 들어갈 때 예보를 다시 안 받아도 돼서 호출 수도 줄임.

## 6. 나만의 추가 (1) - 시간대별 최적 생활지수

과제 5의 생활지수는 지금 이 순간 빨래하기 좋은지만 답했다. 그때는 시점이 하나뿐이었으니 어쩔 수 없었다. 예보가 붙으면서 여러 시점이 생겼길래, 같은 계산식을 시점마다 돌려서 오늘 중 언제가 제일 좋은지를 답하게 만들었다. 계산식은 과제 5에서 만든 순수 함수를 그대로 재사용했고, 새로 만든 건 시점별로 돌려서 최고점을 뽑는 함수 하나뿐이다. 예보 데이터가 없으면 애초에 만들 수 없는 정보라서, 외부 서비스를 추가해서 기능을 확장했다는 요구사항에 가장 정확히 맞는 항목이라고 생각한다. 시간 데이터에는 시간대 정보가 없어서, 날짜 관련 라이브러리로 도시의 시간대에 맞게 옮겨줘야 오늘의 범위와 특정 시각이 제대로 맞는다. 늦은 밤이라 오늘 남은 구간이 없으면 앞으로 24시간을 대신 보여주고 카드 제목도 그에 맞게 바꿨다. 미세먼지는 구간별 예보 값이 없어서 현재 관측값을 전 구간에 똑같이 적용했다.

## 7. 나만의 추가 (2) - 내 위치 날씨와 예외 대응

브라우저의 위치 정보 기능으로 좌표를 받아서 역지오코딩으로 한글 지명을 얻고, 그 좌표의 현재 날씨를 보여주는 기능을 넣었다. 화면에 들어오자마자 권한을 물어보지 않고 버튼을 눌렀을 때만 권한을 요청하게 했다. 화면 들어오자마자 권한 팝업부터 뜨는 것은 별로라고 판단. 거부해도 아래 도시 여섯 곳은 그대로 쓸 수 있다. 통신이 전부 실패하면 임시 데이터로 내려앉고 오프라인 데이터라는 배지를 띄운다. 도시 여섯 곳을 받아올 때는 하나라도 실패하면 전체가 무너지는 방식 대신, 실패한 것과 성공한 것을 구분해서 처리하는 방식을 썼다.

## 8. 호출 수와 캐싱

홈 화면에 진입할 때 도시 여섯 곳에 대해 세 가지 서비스씩 열여덟 번의 요청이 나간다. 상세 페이지에 들어가면 자외선 요청이 하나 더 붙는다. 무료 플랜은 분당 요청 횟수 제한이 있어서 화면을 오가며 테스트하다 보면 금방 다 쓴다. 그래서 저장소에 10분짜리 캐시를 둬서, 캐시가 살아있으면 요청을 아예 안 보내게 했다. 홈을 거치지 않고 통계나 상세 페이지로 바로 들어와도 값이 있어야 해서 그 화면들도 같은 조회 함수를 부르는데, 캐시 덕분에 중복 호출은 생기지 않는다. 별도의 캐싱 전용 라이브러리는 넣지 않았다. 저장소 캐시만으로 충분했고 개발하면서 요청 제한에 걸린 적도 없었다. 필요해지면 그때 붙이는 게 맞다고 생각한다.

## 9. 사용한 라이브러리

통신 라이브러리는 과제 필수. 날짜 관련 라이브러리는 시간을 도시별 시간대로 옮기고 "오늘 오후 몇 시", "몇 분 전" 형태로 표시하는 데 썼다. 설정은 한 곳에 모아뒀고, 기본 기능만 들어있어서 시간대와 상대 시간 표시 기능을 따로 확장해줘야 했다. 자잘한 브라우저 기능을 편하게 쓰게 해주는 라이브러리는 내 위치, 자동 갱신, 오프라인 감지에 썼다. 전역 저장소 값을 브라우저에 남겨주는 라이브러리도 추가해서, 과제 5에서 남겨뒀던 "새로고침하면 값이 초기화된다"는 문제를 이번에 해결했다. 단위 설정, 즐겨찾기, 최근 본 도시 저장소에는 이 기능을 켰지만, 날씨 저장소에는 일부러 안 켰다. 켜면 어제 받아둔 기온이 오늘 화면에 그대로 뜨는 문제가 생긴다. 저장해도 되는 값과 안 되는 값이 갈린다는 걸 이번에 알게 됐다. UI 라이브러리는 로딩, 에러, 빈 상태 표시 정도만 부분적으로 썼고 전체 레이아웃은 기존 스타일을 그대로 유지했다. 서버 데이터 관리를 대신해주는 다른 라이브러리는 일부러 안 썼다. 그쪽으로 넘기면 과제 5에서 배운 전역 저장소의 역할이 사라져버려서, 배운 걸 우회하는 셈이 될 것 같았다.

## 10. 확인한 것

키를 비운 채로 띄우면 요청이 전부 인증 실패로 떨어지고, 홈이 임시 데이터로 내려앉으면서 오프라인 데이터 배지와 에러 문구가 뜬다. 화면이 텅 빈 채로 서있지 않는 걸 확인했다. 같은 상태에서 상세 페이지의 자외선 정보는 정상적으로 표시됐다. 자외선 서비스는 키와 무관한 별개 서버라서, 한쪽이 죽어도 다른 쪽은 사는 구조가 실제로 동작하는 걸 확인했다. 상세 페이지로 바로 들어와도 값이 채워짐. 처음엔 이 경로에서 대체 데이터가 안 걸려서 이상한 값이 표시됐었는데, 저장소에 있으면 그대로, 없으면 받아오고, 실패하면 임시 데이터로 처리하는 함수를 만들어서 수정. 새로고침해도 즐겨찾기, 개인 기준, 최근 본 도시가 그대로 남아있다. 통계 화면의 순위 막대는 값이 오기 전엔 최고 기온이 0이라 0으로 나누는 문제가 있었는데, 이상한 값이 안 들어가도록 분모를 막아뒀다.

## 11. 배포와 인증 키 서버 이전

앞에서 "브라우저에서만 동작하는 앱에서는 키를 완전히 가릴 방법이 없다"고 적어뒀는데, 배포를 준비하면서 그게 말뿐이 아니라 눈으로 직접 확인됐다. 빌드 결과물을 뒤져보니 저장소 관련 파일 안에 키가 문자열로 그대로 들어있었다. 번들에서 문자열만 지운다고 해결되는 문제가 아니었다. 브라우저가 외부 서비스를 직접 호출하는 이상 요청 주소에 인증 키가 그대로 실려 나가고, 그건 개발자 도구의 네트워크 탭에서 다 보인다. 코드를 숨겨도 나가는 요청 자체는 못 숨긴다. 그래서 요청 경로를 하나 더 늘렸다. 브라우저에서 내 서버를 거쳐 외부 서비스로 가는 구조다. 키를 아는 주체를 브라우저에서 서버로 옮김.

무엇을 고쳤는지 정리하면 이렇다. 환경변수 이름을 브라우저에 노출되는 접두사가 붙은 이름에서 접두사가 없는 이름으로 바꿨다. 빌드 도구는 특정 접두사로 시작하는 변수만 브라우저 번들에 넣어주기 때문에, 접두사를 떼는 순간 번들에 들어갈 방법이 없어진다. 접두사가 존재하는 이유가 바로 이 구분이었다. 서버리스 함수 파일을 새로 추가했는데, 이 파일은 브라우저 요청을 받아서 인증 키를 붙여 외부 서비스에 넘기고 응답을 그대로 돌려줌. 이 파일은 서버에서만 실행되고 브라우저로는 내려가지 않는다. 처음엔 대괄호를 쓴 이름 규칙으로 만들었다가 배포 후에 없는 페이지 오류를 만났는데, 그 이름 규칙은 다른 프레임워크의 파일 규칙이고, 별도 프레임워크 없는 프로젝트에서는 서버 함수 폴더 안 파일 하나가 함수 하나로만 매핑된다는 걸 그때 알았다. 함수 작성 방식도 예전 방식이 아니라 웹 표준에 맞는 최신 방식으로 썼다. 하위 경로는 재작성 규칙이 쿼리 파라미터로 넘겨준다. 파일 이름으로 라우팅하지 않고 설정으로 명시해두니까 이름 규칙에 의존하지 않아도 됐다. 아무 경로나 다 중계하면 남이 내 함수를 공짜 프록시로 쓸 수도 있어서, 실제로 쓰는 경로 네 개만 허용하는 화이트리스트를 뒀다. 상태 코드는 그대로 돌려준다. 인증 실패나 요청 제한 초과를 성공으로 바꿔버리면 화면에서 에러 종류를 구분 못 하게 된다. 기존 통신 도구의 기본 주소를 외부 서비스 주소에서 내 서버 주소로 바꾸고, 공통 옵션에서 인증 키를 뺐다. 화면 쪽 코드는 하나도 고치지 않았다. 과제 6에서 주소를 아는 파일을 하나로 몰아둔 덕분에 기본 주소 한 줄만 바꾸면 끝났다. 구조를 나눠둔 게 실제로 값을 발휘한 순간이었다.(AI가 다 해줌)

로컬 개발은 조금 다르게 동작한다. 서버리스 함수는 개발용 서버에서는 실행이 안 돼서, 그냥 두면 로컬에서 전부 없는 페이지 오류가 난다. 개발 도구 설정에 프록시를 넣어서 개발 중엔 개발용 서버가 같은 역할을 하게 했다. 브라우저가 보는 주소는 개발이든 배포든 똑같고, 키를 붙이는 주체만 달라지는 구조다. 환경변수를 불러오는 설정에서 접두사 인자를 빈 문자열로 준 이유는, 기본값이 특정 접두사라서 접두사 없는 변수를 못 읽기 때문이다. 이 설정 파일은 서버 환경에서 실행되니까 키를 다뤄도 안전하다. 빌드 결과물을 확인할 때 쓰는 미리보기 명령에도 같은 프록시를 걸어뒀다. 코드 검사 설정에도 서버 함수와 이 설정 파일만 서버 환경 전용 문법을 쓰도록 블록을 추가했다. 뒤집어 말하면 그 외 파일에서는 서버 전용 값을 못 쓰니까, 키가 브라우저 코드로 새는 걸 검사 도구가 미리 막아주는 셈이다.

자외선 서비스는 그대로 뒀다. 애초에 키가 필요 없는 서비스라 중계할 이유가 없다. 감출 게 없는데 경로만 괜히 길어진다. 덕분에 한쪽 서버가 죽어도 다른 쪽은 산다는 구조도 그대로 유지된다.

남은 한계도 숨기지 않고 적어둔다. 내 중계 주소는 여전히 공개라서, 남이 호출해서 무료 플랜 할당량을 쓸 수는 있다. 다만 키 유출과는 급이 다른 문제라고 본다. 키가 새면 남이 자기 서비스에 갖다 쓰고 내 계정이 정지되지만, 중계 남용은 경로 화이트리스트와 호출 제한으로 대응할 수 있고 주소를 바꾸는 것도 가능하다. 완전히 막으려면 로그인 인증이 필요한데, 로그인 없는 공개 날씨 앱에서는 그렇게까지 할 의미가 없다고 판단했다.

확인해보니 브라우저가 실제로 보내는 요청 주소에 인증 키가 더 이상 붙지 않았다. 빌드 결과물 전체를 키 문자열로 검색해봤는데 한 건도 안 나왔다. 바꾸기 전엔 한 건이 나왔었다. 인증 키 파라미터라는 단어조차 번들에 없다. 중계를 거친 뒤에도 다섯 개 서비스가 전부 정상 동작했다.

# 과제

교수님이 준 참고 파일에서 실제로 쓰인 문법과 라이브러리를 상한으로 두고, 그 안에서 화면 완성도를 올린 단원이다. 계획은 별도 파일에 적어뒀고 여기에는 결과와 판단 근거만 남긴다.

## 1. 이번 단원의 요구사항

외부 UI 라이브러리를 하나 선정해서 지금까지 만든 과제에 자유롭게 적용해보는 게 요구사항이었다. 라이브러리는 엘리먼트 플러스로 확정했다. 과제 6 때 이미 설치와 전역 등록을 해둔 상태였고, 참고 파일에도 같은 라이브러리 실습이 들어 있어서 상한 안쪽인 게 확실했다. 다만 과제 6까지 실제로 쓰던 건 몇몇 컴포넌트뿐이라 설치만 하고 거의 안 쓴 상태에 가까웠다. 이번에 열다섯 종 이상으로 늘렸다. 카드, 버튼, 태그, 배지, 스위치, 체크박스, 입력창, 슬라이더, 라디오 그룹, 진행률, 통계 숫자, 상세 정보, 접기 패널, 타임라인, 결과 화면, 메시지 알림 같은 컴포넌트들이다. 적용 기준은 바꿔서 더 나아지는 곳만으로 잡았다. 잘 돌아가는 걸 라이브러리 컴포넌트로 갈아끼우는 것 자체가 목적이 되면 코드만 길어진다. 직접 만들기 번거롭거나, 키보드 조작이나 접근성을 공짜로 얻는 자리를 골랐다. 새 패키지는 하나도 추가로 설치하지 않았다. 날씨 아이콘은 외부 서비스가 이미 주고 있어서 별도 아이콘 패키지도 쓰지 않았다.

## 2. 인터페이스는 지키고 내부만 갈아끼움

공통 카드 컴포넌트는 과제 3에서 만든 산출물이라 컴포넌트 자체를 없앨 수 없었다. 그래서 컴포넌트를 라이브러리 카드로 통째로 대체하지 않고, 껍데기 안쪽만 라이브러리 카드로 바꾸고 기존의 내용 끼워 넣는 자리는 그대로 뒀다. 결과적으로 이 카드를 쓰는 화면 여섯 개를 한 줄도 안 고쳤다. 끼워 넣는 자리로 인터페이스를 잡아두면 내부 구현을 통째로 바꿔도 부모가 안 흔들린다는 걸 실제로 확인했다.

## 3. 양방향 연결을 쓰지 않은 자리

라이브러리 컴포넌트는 대부분 자동 양방향 연결을 전제로 만들어져 있지만, 두 자리에서는 일부러 값 전달과 이벤트 처리를 따로 붙였다. 하나는 전역 저장소 값을 다루는 컴포넌트들이다. 자동 양방향 연결은 상태에 직접 대입하기 때문에 실행 함수를 건너뛴다. 과제 5에서 미세먼지 경계값 설정 함수 안에 넣어둔 "두 경계가 서로를 넘지 못하게 막는" 검증이 통째로 우회돼버린다. 그래서 읽기는 계산 값으로, 쓰기는 실행 함수를 거치도록 유지했다. 다른 하나는 검색 입력창이다. 과제 1 요구사항의 한글 처리가 값과 입력 이벤트를 직접 연결하는 방식을 요구한다. 자동 양방향 연결은 한글 조합이 끝나야 값이 반영돼서 타이핑 도중 검색이 한 박자 늦다. 라이브러리를 쓰면서도 앞 단원 요구사항을 그대로 지킨 자리다. 반대로 접기 패널의 어떤 항목이 열려 있는지는 화면 안에서만 쓰는 상태라서 자동 양방향 연결을 그대로 썼다. 전역 저장소 값이 아니라서 앞서 말한 원칙과 충돌하지 않는다.

추가로 교수님께서 수업시간에 말씀 하신 AI로 코딩을 짜면 병렬 구조로 코딩을 진행한다라는 언급을 하셨기 때문에 병렬보다는 단방향 코딩으로 진행하려고 노력. 각자 장단점이 있을 수 있긴 하지만 가능하다면 단방향 코딩을 진행하려고 했음.

## 4. 받아만 두고 안 쓰던 데이터를 화면에 씀

외부 날씨 서비스가 날씨 아이콘 코드를 함께 주고 있었고 저장소에도 자리가 있었는데, 과제 6까지는 이걸 그리는 화면이 하나도 없었다. 카드와 상세 페이지 상단에 아이콘 이미지를 붙였다. 추가 호출은 전혀 없다. 이미 응답에 들어 있던 값이기 때문이다. 상세 페이지 상단 배경은 아이콘 코드의 앞 두 자리로 날씨 종류를 판정해서 클래스를 갈아끼웠다. 색을 스타일에 고정해두지 않고 데이터가 클래스를 고르게 했다. 임시 데이터에는 아이콘 값이 없어서, 조건부 렌더링으로 자동으로 걸러지고 오프라인 상태에서 깨진 이미지가 뜨지 않는다.

## 5. 검색어를 한 방향으로 정리

과제 6까지는 화면에 들어올 때 주소에서 상태로, 검색어가 바뀔 때 상태에서 주소로, 양쪽으로 값이 흘렀다. 값 하나에 저장소가 둘이고 서로를 갱신하는 구조였다. 동작에는 문제가 없었지만 뒤로 가기로 주소가 바뀌면 화면이 안 따라왔다. 화면에 들어올 때만 실행되는 코드는 처음 한 번만 돌기 때문. 그래서 주소창 하나를 원본으로 정하고 화면은 거기서 파생만 하도록 바꿨다. 검색어를 계산 값으로 만들어서 주소의 검색 조건을 그대로 읽어오게 하고, 검색어를 바꾸는 처리는 주소를 갱신하는 것 하나로 통일. 흐름이 입력에서 주소 갱신, 주소 읽기, 계산 값, 화면 순서로 한 방향이 되면서 복원 코드와 동기화 감시가 둘 다 사라졌다. 코드가 줄었는데 기능은 늘었다.

## 6. 데이터를 받아오는 지점을 한 곳으로

과제 6까지 날씨 전체를 받아오는 함수를 홈, 즐겨찾기, 통계, 설정 네 화면이 각자 화면에 들어올 때 불렀다. 캐시 덕에 중복 호출은 안 났지만, 언제 받아오는지를 아는 곳이 네 곳이었다. 이걸 전체 화면 껍데기 한 곳으로 올렸다. 이제 각 화면은 저장소를 읽기만 한다. 데이터 흐름이 화면 껍데기에서 한 번 요청하고, 저장소를 거쳐, 각 화면이 읽기만 하는 한 줄로 정리됐다. 상세 페이지에서 특정 도시만 채우는 함수는 그대로 뒀다. 이 도시만 없으면 채운다는 역할이 다르기 때문이다. 10분마다 자동 갱신하는 기능도 홈에 남겨뒀다. 화면 껍데기로 올리면 보지도 않는 화면 때문에 호출 한도를 쓰게 된다.(실패한 것과 성공한 것을 구분해서 처리하는 방식과 전부 성공해야 하는 방식을 각각 쓰던 부분은 그대로 뒀는데, 그 근거는 뒤쪽에 따로 정리)

## 7. 같은 계산을 두 화면이 나눠 쓰게 함

홈 상단에 평균 기온, 평균 습도, 가장 더운 곳, 미세먼지 나쁨 개수를 보여주는 요약 타일을 넣으면서, 통계 화면에 있던 계산식을 복사할 뻔했다. 복사하면 평균 구하는 방식이 두 곳에 생겨서 나중에 갈라진다. 그래서 날씨 저장소에 요약 계산 값을 하나 만들어서 홈과 통계가 같은 것을 읽게 했다. 다만 미세먼지 나쁨 개수는 이 요약 계산 값에 넣지 않음. 그 판정 기준은 사용자가 설정 화면에서 정하는 값이라 단위 설정 저장소 소관인데, 날씨 저장소가 단위 설정 저장소를 끌어다 쓰면 저장소끼리 얽히게 되기 때문에 등급이 걸린 집계만 화면 쪽에서 계산했다.

## 8. 레이아웃

카드 목록을 세로 한 줄에서, 화면 너비에 맞춰 열 수가 자동으로 바뀌는 그리드로. 별도의 화면 크기 분기 없이 폰에서는 한 열, 태블릿에서는 두 열, 데스크톱에서는 세 열이 된다. 상세 화면은 아이콘과 큰 기온, 날씨별 배경이 들어간 상단 영역을 위에 두고, 관측 항목 표는 라이브러리의 상세 정보 컴포넌트로, 시간별 예보는 가로로 스크롤되는 카드로 바꿨다. 도시 이동 버튼을 맨 아래에서 상단 영역 옆으로 올려서 스크롤 없이 옆 도시로 넘어갈 수 있게 했다. 로딩 중 뼈대 화면을 실제 카드 그리드와 같은 격자 모양으로 맞췄다. 과제 6의 단순한 줄 형태는 실제 카드와 안 닮아서 로딩이 끝나는 순간 화면이 튐. 페이지가 바뀔 때 부드럽게 전환되는 효과도 얹었다. 기본 문법만으로 만들어서 라이브러리 추가가 없고, 참고 파일에도 비슷한 조합이 주석으로 들어 있어서 형태 자체는 배운 범위 안이다.

## 10. 스캐폴드 잔재를 걷어냄

기본 스타일 파일에 프로젝트를 처음 만들 때 자동으로 생긴 화면 분할 규칙이 그대로 남아 있어서, 화면 절반이 영구적으로 빈 공간이 되는 문제가 있었다. 공통 컨테이너 스타일에도 최대 너비 지정 뒤에 고정 너비가 다시 지정돼서 최대 너비 규칙이 무력화된 부분이 있었다. 어떤 화면에서도 본문이 800픽셀로 고정돼 있었고, 실제로 재보니 좁은 화면에서 47픽셀만큼 가로 스크롤이 생겼다. 둘 다 정리해서 너비를 화면에 맞게 유동적으로 바꾸고 최대 너비만 제한하는 방식으로 고쳤다.

## 11. 확인한 것

아홉 개 페이지를 전부 열어 가로 넘침이 없고 콘솔 에러도 없는 걸 확인했다. 홈에서 도시 카드 여섯 장에 아이콘이 붙고, 그리드가 화면 폭에 따라 열 수를 바꾼다. 상세 페이지에서 아이콘 코드에 따라 상단 배경이 갈린다. 설정에서 슬라이더를 움직이면 홈과 통계의 판정이 같이 바뀌고, 새로고침해도 유지된다. 없는 도시 코드는 라이브러리의 결과 화면 컴포넌트로, 없는 주소는 404 화면으로 각각 떨어진다. 레거시 페이지의 과제 1~3 화면이 그대로 살아 있고 색만 새 톤을 따라온다. 톤을 적용한 뒤 실제로 화면을 측정해서 카드 배경, 테두리 색, 모서리 반경, 그림자 없음, 각 화면의 글자 크기가 의도한 값과 일치하는 걸 확인했다. 좁은 화면에서도 상세 페이지 기온 글자가 알맞게 줄어들고 가로 넘침이 없는 걸 확인했다. 전체 소스에서 색상 코드를 전수 조사해봤는데, 날씨 삽화 그라데이션 다섯 개를 제외하고는 하드코딩된 색이 없었.

## 12. 통신 호출 형태 정리

점검해보니 이 프로젝트에는 그 방식이 한 건도 없었다. 서비스 함수 다섯 개가 전부 짧은 형태의 호출 방식으로 되어 있고, 옵션 객체를 직접 조립하는 방식은 쓰지 않았다.

근거는 세 가지다. 첫째는 성능이다. 실측해보니 홈 화면 첫 로딩에 나가는 요청이 열아홉 개, 평균 응답 시간이 700밀리초 정도, 전부 순서대로 하나씩 바꾸면 합계 13초 넘게 걸린다. 지금은 1~2초 안에 끝난다. 화면을 열 때마다 13초를 기다리는 쪽이 잃는 게 더 크다. 둘째, 실패한 것과 성공한 것을 구분해서 처리하는 방식은 성능을 위한 장치가 아니라 기능을 위한 장치다. 전체 날씨를 받아오는 함수는 실패한 도시 개수를 세서 대체 데이터를 쓸지 말지 정한다. 전부 실패하면 임시 데이터로 내려앉고 일부만 실패하면 알림만 띄운다. 순서대로 하나씩 기다리는 방식은 첫 실패에서 멈추기 때문에 이 로직을 처음부터 다시 짜야 한다. 셋째, 이건 값이 어디서 어디로 흐르는지와는 무관한 문제다. 동시에 여러 요청을 기다리는 것은 몇 개를 동시에 기다리는가만 정할 뿐이고, 6번에서 정리한 한 방향 원칙과는 다른 축의 이야기다. 정리하면, 통신 라이브러리가 제공하는 병렬 요청 전용 방식은 쓰지 않고, 표준 자바스크립트의 동시 처리 기능만 필요한 자리에 썼다.

## 13. 나만의 추가 - 날씨가 화면 배경이 되는 연출

상세 페이지에 들어가면 그 도시의 실제 날씨가 화면 전체 배경이 된다. 비가 오면 빗줄기가 내리고, 눈이 오면 눈이 날리고, 흐리면 구름이 흘러간다. 추가 서비스 호출은 없다. 과제 6부터 이미 받아오고 있던 아이콘 코드 하나만 쓴다. 이 코드는 앞 두 자리가 날씨 종류를, 마지막 한 자리가 낮인지 밤인지를 나타내는 구조라, 값 하나로 여섯 종류의 날씨와 낮밤을 합쳐 열두 가지 상태가 나온다. 맑을 때는 햇빛 속 먼지처럼 오르내리는 점을, 밤에는 반짝이는 별로 바꿔서 보여준다. 구름일 때는 흐릿한 큰 덩어리가 가로로 아주 느리게 흐르고, 비가 올 때는 가는 빗줄기가 아래로 떨어진다. 뇌우일 때는 빗줄기에 더해 몇 초에 한 번씩 화면이 짧게 두 번 번쩍인다. 눈이 올 때는 동그란 눈이 좌우로 밀리며 천천히 내리고, 안개일 때는 반투명한 띠가 옆으로 아주 느리게 흐른다.

이렇게 만든 이유는, 강의 자료의 "데이터가 조건과 바인딩을 거쳐 화면 변화까지 이어지게" 하고 "색상을 하드코딩하지 않고 조건부 스타일로 동적으로 표현" 하라는 지침을 가장 크게 적용한 자리이기 때문이다. 색을 스타일에 미리 박아두고 고르는 게 아니라, 실제 값이 클래스와 스타일을 직접 고른다. 입자는 반복 출력으로 만들고 위치, 속도, 투명도, 크기를 하나씩 다르게 지정했다. 전부 같은 값이면 줄이 맞아서 비가 아니라 창살처럼 보인다. 무작위 값은 계산 값 안에서 뽑기 때문에 날씨 종류가 바뀔 때만 다시 생성되고, 기온이 갱신되는 정도로는 다시 계산되지 않는다. 입자 개수는 비가 가장 많고 뇌우, 눈, 구름, 맑음, 안개 순으로 적어진다. 눈으로 직접 보면서 정한 값이고, 늘리면 그럴듯해지지만 화면 요소가 그만큼 늘어난다.

성능을 위해 몇 가지를 지켰다. 위치를 직접 옮기는 대신 이동과 투명도만 애니메이션으로 처리했다. 위치 값을 매 프레임 움직이면 그때마다 레이아웃을 다시 계산해서 입자가 많아질수록 눈에 띄게 끊기지만, 이동과 투명도는 그래픽 처리 장치에 넘길 수 있다. 입자 개수만큼 애니메이션을 각각 만들 수는 없어서, 애니메이션은 하나만 두고 값만 스타일 변수로 주입하는 방식을 썼다. 예를 들어 눈이 좌우로 밀리는 정도는 각 입자마다 다른 값을 내려보내고 애니메이션 안에서 그 값을 읽는다. 애니메이션 시작 지점을 음수로 줘서 화면에 들어온 순간 이미 떨어지는 중인 것처럼 보이게 했다. 0부터 시작하면 처음 1초간 화면 위쪽이 비어서 이제 막 비가 시작되는 것처럼 보인다. 빌드해보니 메인 번들 용량은 사실상 그대로였고, 늘어난 용량은 상세 화면 전용 파일에만 들어갔다. 상세 페이지는 지연 로딩 대상이라 첫 화면 로딩에는 영향이 없다.

접근성도 신경 썼다. 운영체제에 동작 줄이기 설정이 켜져 있으면 입자를 아예 감추고 하늘 톤만 남긴다. 움직이는 배경에 어지러움을 느끼는 사람이 있기 때문이다. 이 경우에도 날씨 정보는 배경 색으로 그대로 전달된다. 배경이 클릭을 가로채지 않도록 하고 스크린리더가 읽지 않도록 처리도 넣었다. 배경이 클릭을 가로채면 그 아래 버튼이 안 눌리고, 스크린리더가 의미 없는 입자 요소를 여러 개 읽으면 안 되기 때문이다. 본문은 배경보다 위 레이어로 둬서 빗줄기가 글자 위로 지나가지 않게 했다.

확인해보니 날씨 종류 판정 함수는 실제로 쓰이는 코드와 잘못된 값 여러 가지로 검사해봤을 때, 빈 값이나 모르는 코드는 전부 알 수 없음으로 떨어지고 그때는 아무것도 그리지 않는다. 임시 데이터에는 아이콘 값이 없기 때문에 통신이 끊긴 상태에서는 배경 연출이 자동으로 꺼진다. 밤에 비가 오는 도시로 들어가면 빗줄기 여러 개가 각각 다른 위치와 속도, 투명도로 생성되는 것과, 상단 영역과 배경이 같은 날씨로 갈리는 것을 확인했다. 배경 위에서도 메뉴 링크와 상단 영역 버튼이 정상적으로 눌리는 것을 확인했다.

## 3. 차트가 첫 화면까지 따라오던 문제

차트를 붙이면서 차트 라이브러리를 별도 묶음으로 빼뒀다. 통계와 상세 화면에서만 쓰는 코드라 그 두 화면에 들어갈 때 내려받게 하려는 의도였고, 설정 주석에도 그렇게 적어뒀다.

그런데 빌드 결과를 실제로 열어보니 반대였다. 첫 화면 문서에 이 묶음이 미리 받아두라는 표시로 걸려 있었고 시작 파일이 직접 참조하고 있었다. 빌드 결과물을 로컬에 띄워 네트워크를 확인하니, 차트가 하나도 없는 대시보드를 여는데 차트 코드 563KB(압축 후 191KB)가 같이 내려오고 있었다. 묶음을 나누는 것과 늦게 내려받는 것은 다른 얘기인데, 파일이 따로 떨어진 것만 보고 됐다고 판단한 것이 원인이었다.

원인은 묶음을 강제로 지정한 설정 자체였다. 이름을 붙여 묶으라고 지시하면 그 묶음이 시작 지점의 고정 의존성으로 끌려 올라간다. 지시를 빼고 자동 분할에 맡기니 첫 화면 문서에서 사라졌다. 차트를 쓰는 두 화면이 이미 지연 로딩이라 자동 분할이 알아서 그 경계 뒤로 넘겨준다.

다만 자동 분할에 맡기면 묶음 이름을 안에 들어간 파일 중 알파벳 순으로 처음 만난 것에서 물려받는다. 563KB짜리 차트 묶음이 차트 색상 설정 파일 이름을 달고 나왔다. 과제 8에서 저장소 파일이 74KB로 보이던 것과 같은 문제다. 그래서 자동 분할은 그대로 두고, 파일 이름을 정하는 자리에서 차트 라이브러리가 들어 있는 묶음만 골라 이름을 붙여주도록 했다. 여기서 한 번 헛디뎠는데, 묶음 안의 파일 목록이 배열인데 객체로 다루는 바람에 조건이 늘 거짓이 되어 이름이 안 바뀌었다. 값의 실제 모양을 찍어보고 나서야 알았다.

고친 뒤 다시 확인했다. 대시보드를 열 때 차트 묶음 요청이 없고, 통계 화면으로 넘어가는 순간 그때 요청이 나간다. 차트는 정상적으로 그려진다. 첫 화면이 압축 기준 191KB 가벼워졌다. 과제 8에서 UI 라이브러리를 필요한 것만 불러오도록 바꿔 얻은 이득과 비슷한 크기를, 설정 한 줄 때문에 도로 반납하고 있었던 셈이다. 얻은 것 하나 - 묶음을 나눴다는 것의 완료 조건은 파일이 따로 생기는 게 아니라, 첫 화면 요청 목록에 그 파일이 없는 것이다.

## 4. 화면이 사라지자 딸려 나온 것들

레거시 페이지를 지우고 저장소를 훑어보니 그 화면 하나가 붙잡고 있던 것이 생각보다 많았다.

과제 1~3에서 만든 컴포넌트 스물두 개가 통째로 고아가 됐다. 어디서도 불러오지 않는데 파일만 108KB 남아 있었다. 번들에는 안 들어가니 배포에는 영향이 없지만, 저장소를 여는 사람에게는 살아 있는 코드와 구분되지 않는다. 게다가 부작용이 하나 있었다. 컴포넌트를 자동으로 찾아 등록해주는 도구가 이름이 겹친다며 경고를 세 줄 띄우고 있었는데, 그중 하나가 지금 실제로 쓰는 날씨 카드였다. 죽은 파일이 살아 있는 파일의 이름을 가리고 있었던 것이다. 폴더를 지우니 경고 세 줄이 전부 사라졌다.

전역으로 깔려 있던 과제 1~3용 공통 스타일 파일도 정리했다. 과제 7에서 이 파일을 두고 "죽은 코드가 아니라 갈라진 코드"라 적고 지우지 않았는데, 그 근거가 과제 1~3 컴포넌트 열여섯 개가 쓰고 있다는 것이었다. 그 열여섯 개가 사라졌으니 근거도 같이 사라진 셈이다. 클래스를 하나씩 대조해보니 살아 있는 화면이 쓰는 규칙은 하단 상태바 하나뿐이었고 나머지는 전부 각 컴포넌트가 자기 스타일로 같은 내용을 갖고 있었다. 상태바 규칙만 실제 사용처인 홈 화면 안으로 옮기고 파일을 지웠다. 옮기면서 모서리 둥글기와 글자 크기를 화면의 다른 상자들과 같은 값으로 맞췄다. 과제 1 때 정한 숫자가 토큰으로 옮겨지지 않고 혼자 남아 있던 자리였다.

라우터에는 UI 라이브러리 캐러셀 예제를 확인하려고 만든 주소가 하나 남아 있었다. 공식 문서 예제를 그대로 복사한 것이라 화면에 1, 2, 3, 4라는 숫자만 뜨고 날씨 앱과 아무 관계가 없었다. 메뉴에도 없고 소개 페이지의 주소 목록에도 없어서 주소를 직접 치지 않으면 닿을 수 없는 페이지였다. 확인이 끝난 도구는 남겨둘 이유가 없다고 보고 화면과 라우트를 함께 지웠다.

## 5. 자정을 정오로 읽히게 적고 있었다

상세 페이지의 "가장 좋은 시간"에 "내일 오전 12시"라고 떠 있었다. 날짜 라이브러리에 오전/오후와 12시간제를 조합해 넘겼기 때문인데, 자정이 이 형식에서는 오전 12시가 된다. 한국어에서 오전 12시는 정오로 읽히기 쉽다. 시각 하나를 열두 시간 어긋나게 읽히도록 적고 있었던 셈이다. 자정과 정오 두 시각만 우리말 표현으로 갈라주고 나머지는 그대로 뒀다. 이제 "내일 자정", "내일 정오"로 뜬다. 숫자 형식을 그대로 믿고 넘긴 자리에서 이런 것이 나온다는 걸 알게 됐다.

## 6. 확인한 것

여덟 개 페이지를 전부 열어 가로 넘침과 콘솔 에러가 없는 것을 확인했다. 폰 크기에서도 같이 확인했다. 대시보드에 광주 카드가 붙어 도시가 일곱 장이 되고, 통계 화면이 일곱 곳 기준으로 집계하며, 기온 순위에도 광주가 들어간다. 상세 페이지에 광주 주소로 바로 들어가도 값이 채워지고 이전, 다음 도시 이동도 정상이다. 빌드 결과물을 띄워 네트워크를 확인했다. 대시보드를 열 때 차트 묶음 요청이 없고 통계 화면에 들어가는 순간 요청이 나간다. 두 화면 모두 차트가 그려진다. 전역 스타일 파일을 지운 뒤에도 홈 하단 상태바의 배경과 테두리, 정렬이 그대로이며 모서리 둥글기만 다른 상자들과 같은 값으로 통일됐다. 지운 주소로 들어가면 404 화면으로 떨어진다. 코드 검사는 경고 없이 통과했고 컴포넌트 이름 충돌 경고 세 줄도 사라졌다. 테스트는 3개 파일 29개가 전부 통과한다.

## 7. 마지막으로 수정한 부분

마지막 수정은 12시를 조금 넘긴 시각이다. 해당 수정을 한 이유는 낡은 주석과 필요없는 코드들을 정리하기 위함으로 실행에는 아무런 영향이 가지 않아서 진행하였다.
