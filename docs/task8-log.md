# 과제 8

과제 7 까지로 기능은 다 붙었다. 이 단원에서 한 일은 두 가지로 갈린다 -
화면 배치를 다시 짠 것(8-1~8-3)과, 미뤄뒀던 정리를 끝낸 것(8-4~8-9)이다.

## 1. 화면 배치 재구성

- 순서를 "찾기 → 보기 → 곁들이기" 로 바꿨다. 이 앱을 여는 이유는 도시 날씨를 보는 것인데,
  과제 7 까지는 검색·내 위치·즐겨찾기 카드가 먼저 나오고 도시 카드가 맨 아래였다.
- 검색은 카드 껍데기를 벗기고 본체 카드 안쪽 맨 위에 긴 바 하나로 넣었다.
  BaseDashboardCard 를 한 장 덜 쓰게 됐지만 슬롯 인터페이스도 SearchBar 의 props/emits 도 그대로다.
- 보조 카드는 2×2 → 3열 auto-fit. "최근 본 도시" 는 기록이 없으면 사라지므로 고정 열 수를 쓰면
  오른쪽 한 칸이 빈 채로 남는다.
- 상단 크롬 압축: 1280px 에서 본문이 시작되기까지 213px 을 헤더/네비가 쓰고 있었다.
  헤더 90 → 62, 네비 54 → 43. 메뉴는 7개 전부 그대로 노출한다 - 숨기면 채점자가 과제 화면을
  클릭 두 번으로 찾아야 한다.
- 모바일 회귀 수정: 375px 에서 요약 타일이 세로 4개(380px)로 쌓이던 것을 2열(184px)로.
  `minmax` 하한이 컨테이너보다 커지는 구간을 미디어쿼리로 없앴다.

## 2. Element Plus 온디맨드 전환

과제 7 의 main.js 에 "화면이 확정된 뒤에 정리하는 게 순서" 라고 적어둔 것을 여기서 끝냈다.

`app.use(ElementPlus)`(전체 등록)를 지우고 `unplugin-vue-components` 로 바꿨다.
템플릿을 훑어 실제로 등장한 `<el-xxx>` 만 골라 import 문으로 바꿔 넣는 방식이라,
개별 등록의 이득(쓰는 것만 들어감)을 가져오면서 "import 를 빠뜨린다" 는 위험은 없다.

| 항목        |  전 (전체 등록) |          후 (온디맨드) |
| ----------- | --------------: | ---------------------: |
| 첫 화면 JS  |     1,087,907 B |              314,999 B |
| 첫 화면 CSS |       373,736 B |               84,290 B |
| 합계        | **1,461,643 B** | **399,289 B** (-72.7%) |

(`index.html` 이 직접 참조하는 파일들의 합. 같은 소스에서 설정만 바꿔 두 번 빌드해 비교했다.)

걸린 지점 두 가지.

- **CSS 순서.** Element Plus 와 우리 base.css 가 둘 다 `:root` 에 변수를 정의해서 나중에 불린 쪽이 이긴다.
  온디맨드로 바꾸면 컴포넌트 CSS 가 각 컴포넌트 파일에서 불려 main.css 보다 뒤로 간다.
  다만 컴포넌트별 CSS 파일에는 `:root` 정의가 없고 `--el-*` 를 참조만 한다. 변수 정의는
  `theme-chalk/base.css` 한 곳에 있으므로, main.js 맨 위에서 그 파일만 먼저 불러 자리를 잡아두면 된다.
  (ES 모듈은 한 번만 평가되므로 나중에 누가 다시 import 해도 순서는 여기서 정해진다.)
- **ElMessage / ElMessageBox.** 템플릿이 아니라 코드에서 부르는 것이라 플러그인 눈에 띄지 않는다.
  스타일이 안 붙어서 흰 배경에 테두리 없는 알림이 떴다. 해당 화면에서 CSS 를 직접 import 해 해결.

## 3. 공통 청크 이름 정리 (`manualChunks`)

vue/pinia/router 가 들어간 74KB 짜리 공통 청크가 `configStore-CKgBNols.js` 라는 이름으로 나오고 있었다.
Rollup 이 청크 이름을 "그 안에 든 모듈 중 알파벳 순으로 처음 만난 것" 에서 물려받기 때문인데,
dist 를 열어본 사람은 스토어 파일이 74KB 라고 읽게 된다. `vendor-vue` / `vendor-utils` 로 이름을 붙였다.
element-plus 는 일부러 묶지 않았다 - 지금은 컴포넌트별로 쪼개져서 캐러셀·타임라인처럼
특정 화면에서만 쓰는 것은 그 화면에 들어갈 때 내려받는다.

## 4. composable 레이어 신설

`@vueuse/core` 를 쓰기만 하고 직접 만들어 본 적은 없었다. 그 결과 화면 파일이 636줄 / 638줄이 됐다.
Composition API 를 `setup()` 문법으로만 쓰고 정작 "조합" 은 안 한 상태였다.

- `composables/useQueryParam.js` — "주소창이 원본, 화면은 파생" 패턴.
  검색어(`?search=`)와 배경 미리보기(`?preview=`) 두 곳에 같은 코드가 복사돼 있었다. 두 번 나왔으면 뽑아야 한다.
- `composables/useMyLocation.js` — 권한 요청 · 좌표 유효성 · 지명/날씨 2단 호출 · 거부 처리.
- `composables/useCityForecast.js` — 오늘 구간 자르기 · 최적 시간대 · 막대 높이 · 시각 라벨.

**여기서 해결되지 않은 것.** 처음에 이 작업 결과를 "Home 636 → 약 380줄" 이라고 적었다가 틀렸다.
`wc -l` 로 재보니 607줄이었다. 227줄 차이다. 블록별로 나눠보면 왜 그런지 바로 보인다.
(아래는 과제 8 을 전부 끝낸 뒤 다시 잰 값이다. `wc -l` 과 블록별 카운트를 같이 돌렸다.)

| | 전 | 후 |
|---|---:|---:|
| Home `<script>` | 153 | **109** |
| Home `<template>` | 170 | 183 |
| Home `<style>` | 246 | **246** |
| Home 합계 | 636 | 610 |
| Detail `<script>` | 231 | **198** |
| Detail `<template>` | 153 | 153 |
| Detail `<style>` | 226 | **226** |
| Detail 합계 | 638 | 605 |

즉 composable 추출은 script 를 44줄(153→109) 줄였고 그게 이 작업이 겨냥한 전부다.
파일이 600줄인 진짜 이유는 로직이 아니라 **뷰마다 다시 쓰는 레이아웃 CSS** 다.
`.city-grid` / `.summary-row` / `.utility-grid` / `.hero-*` 가 전부 "카드를 격자에 깐다" 는
같은 문제를 화면마다 새 이름으로 푼다. base.css 에 토큰은 잡혀 있는데 배치 패턴은 공유되지 않는다.
(`WeatherBackdrop.vue` 는 454줄 중 296줄이 style 이다.)

지금 손대지 않는다 — 제출 직전 CSS 리팩터링은 회귀 위험만 크다.
다만 "줄었다" 가 아니라 "script 는 뺐고 style 246줄은 그대로 남았다" 로 적어둔다.
남은 것을 아는 상태와 해결했다고 믿는 상태는 다르다.

안 보이는 것과 없는 것은 다르다.

## 6. 테스트 (vitest)

순수 함수로 뽑아두기만 하고 검증은 안 하고 있었다. 눈으로는 틀린 것을 알 수 없는 세 곳을 잡았다.

| 대상                                     | 왜                                                                       |
| ---------------------------------------- | ------------------------------------------------------------------------ |
| `data/lifeIndex.js` 의 `getBestTimeList` | 이 프로젝트의 유일한 독자 알고리즘. 점수가 틀려도 그럴듯한 시각이 찍힌다 |
| `configStore.dustGrade`                  | 경계 30/80 이 한 칸 밀리면 세 화면의 색과 문구가 동시에 틀어진다         |
| `weatherStore.summary`                   | 홈과 통계가 같이 읽는 집계. 평균 자릿수·정렬 부작용·경계(40%)            |

`npm test` → 3 files / 29 tests.

`summary` 테스트를 쓰다가 버그를 하나 찾았다.
`cityList` 가 `EMPTY_WEATHER` 로 항상 6칸을 채우기 때문에 통신 전에도 `summary` 가 null 이 아니다.
그래서 첫 진입 1~2초 동안 "평균 기온 0.0℃ · 가장 더운 곳 서울 0.0℃" 가 화면에 떠 있었다.
카드 그리드는 `isFirstLoading` 으로 스켈레톤을 깔고 있는데 요약 타일만 빠져 있었던 것이다.

처음에는 화면에서 `v-if="hasData && summary"` 로 막았는데, 실제 로딩 과정을 70ms 간격으로
찍어보니 그것으로는 부족했다. `hasData` 는 도시 한 곳만 도착해도 참이 되므로,
1곳 실측 + 5곳 0℃ 를 6으로 나눈 "평균 11.2℃" 가 여전히 잠깐 뜬다.

원인은 화면이 아니라 집계 쪽에 있었다. `cityList` 는 "화면이 NaN 을 그리지 않게" 만든 목록인데
집계가 같은 목록을 쓰고 있었다. 그릴 목록과 셀 목록을 갈랐다 —
`loadedCityList`(관측값이 실제로 도착한 도시만)를 만들고 `summary` 가 그것을 본다.
한 곳도 없으면 `null` 이라 화면은 `v-if="summary"` 하나로 갈린다.
같은 조건을 이미 쓰고 있던 통계 화면(`el-empty`)의 빈 상태도 그제야 실제로 동작하게 됐다.

다시 찍어보니 0℃ 도 부분 평균도 나오지 않고, 도시가 도착하는 대로 31.8 → 33.5 → 32.8 → 32.7 로만 움직인다.

## 7. 스토어 방어

- **동시 요청 가드.** `fetchAll` 이 캐시(`isFresh`)만 보고 진행 중인 요청은 안 봤다.
  첫 로딩(1.2~2초) 중에 새로고침 버튼을 누르면 `force: true` 라 캐시를 지나쳐 18회가 한 벌 더 나간다.
  버튼의 `:loading` 이 가려주고 있었을 뿐이다. 상태를 지키는 일을 UI 에 맡기면 호출부가 늘 때마다
  같은 구멍이 다시 생긴다. 진행 중인 Promise 를 들고 있다가 그대로 돌려주는 방식으로 막았다.
- **로딩 깃발 분리.** `fetchAll` 과 `ensureCity` 가 `isLoading` 하나를 같이 쓰고 있었다.
  상세 화면의 로딩이 끝날 때 대시보드의 스켈레톤 판정까지 같이 꺼진다. `isCityLoading` 으로 갈랐다.
- **상대시간이 안 흘렀다.** `lastFetchedLabel` 이 `lastFetched` 에만 의존해서, 다음 갱신(10분 뒤)까지
  "몇 초 전" 으로 굳어 있었다. 30초마다 깨어나는 `now` ref 를 의존성에 추가.

## 8. 서버리스 함수 하드닝

경로 화이트리스트는 "무엇을" 만 막고 "얼마나 자주" 는 막지 않았다.
방문자 한 명이 18회를 쓰는데 클라이언트 캐시는 Pinia 메모리라 새로고침 한 번에 사라진다
(weatherStore 는 의도적으로 persist 를 끈 스토어다). 채점자 몇 명이 새로고침을 반복하면
무료 플랜 분당 60회에 닿는다.

- `Cache-Control: s-maxage=600` — Vercel 엣지가 지키는 값이다.
  도시 좌표가 고정이라 주소도 고정이므로, 방문자가 몇 명이든 원본 호출은 10분당 18회로 묶인다.
  캐시 유효시간은 프런트의 `CACHE_DURATION`(10분)과 맞췄다.
- 실패 응답(401/429/502)에는 `no-store`. 원인을 고친 뒤에도 10분간 같은 에러를 보게 되면 안 된다.
- `Origin` 확인 — 다른 사이트가 자기 페이지에서 이 함수를 부르는 것을 막는다.
  한계는 분명하다. curl 이나 서버 스크립트는 Origin 을 안 보내므로 통과한다. 그쪽은 엣지 캐시가 맡는다.

### 8-1. 그 캐시가 방금 고친 상대시간을 다시 거짓말시켰다

`stale-while-revalidate=1800` 을 같이 걸어뒀는데, 이게 바로 위에서 맞춰둔 것을 스스로 깼다.

SWR 창 안에서는 엣지가 "만료됐지만 아직 새로 못 받은" 값을 그대로 준다.
`s-maxage=600` 은 10분에 맞췄어도 SWR 이 창을 30분 더 늘리므로, 최악의 경우 이런 상태가 된다.

```
엣지 : 25분 전에 받아둔 값을 즉시 반환   (SWR 창 안)
클라 : lastFetched = 방금  →  "몇 초 전 기준" + 실시간 관측 태그
실제 : 25분 전 데이터
```

원인은 캐시가 아니라 **라벨이 가리키는 값**이었다.
`lastFetched` 는 "우리가 요청한 시각" 이지 "관측한 시각" 이 아니다.
로컬 개발에서는 Vite 프록시가 캐시를 하지 않아 둘이 항상 같으므로 절대 재현되지 않고, 배포 후에만 갈라진다.

고칠 재료는 이미 받아두고 있었다. `api/weather.js` 가 OpenWeatherMap 응답의 `dt`(관측 시각, UNIX 초)를
`observedAt` 으로 번역해 스토어까지 올려두고 있는데, **어느 화면도 쓰지 않고 있었다.**
전수 검색 결과 `weather.js` 와 `EMPTY_WEATHER` 정의부 두 곳에만 존재했다.

과제 7 에서 `icon` 을 두고 지적한 것과 정확히 같은 상태다 — 받아만 두고 화면에서 안 쓰는 데이터.

```js
// weatherStore.js
// 화면에 뜬 값 중 "가장 오래된" 관측 시각. 여섯 곳 중 한 곳이라도 오래되면 "방금" 이라고 하면 안 된다.
const oldestObservedAt = computed(() => { ... Math.min(...stamps) * 1000 })

const observedLabel = computed(() => {
  void now.value                                        // 30초 시계(위 7번 항목)
  const stamp = oldestObservedAt.value ?? lastFetched.value  // 목업 폴백엔 dt 가 없다
  return stamp ? fromNow(stamp) : ''
})
```

화면 문구도 `"… 기준"` → `"… 관측"` 으로 바꿨다. 추가 호출 0회, 새 의존성 0개다.
게터 이름도 `lastFetchedLabel` → `observedLabel` 로 바꿨다. 가리키는 것이 달라졌으므로 이름도 달라져야 한다.

SWR 은 그와 별개로 `1800` → `120` 으로 줄였다.
라벨이 정직해졌으니 거짓말은 안 하지만, 사용자가 40분 된 값을 볼 이유 자체가 없다.
뒤에서 도는 재검증은 1초 안에 끝나므로 2분이면 몰림을 흡수하기에 충분하다.

## 9. 마감 정리

- `<html lang="">` → `lang="ko"`. 한국어 서비스인데 스크린리더가 언어를 몰랐다.
